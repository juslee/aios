- Branch `claude/cap-lifetime`, in a worktree created from `main` b07d7e4 before the docs PR that carries the ADR and the crash-fix amendment merged. Its first commit (c97caa0) adds this plan. Every update from `main` is a merge, never a rebase, and nothing is force-pushed, so c97caa0 stays the plan's first commit (owner, 2026-09-28; "Decisions Made"). The ADR says "rebased" for these updates; they are carried out as merges, and step 16 notes that on the ADR (§3 step 16). Step 1 starts once the no-new-kwarn baseline has been taken from a boot of f410589 (owner, 2026-09-29: implementation starts only after crash-fix steps 1a, 1b and #200's fix step merged; all three are in f410589). One commit per step, named `Cap lifetime step N: <description>`, pushed once the step's checks pass.
- Every commit passes `just check` (zero warnings) and `just test`.
- **Boot checks** use `just run` and grep the UART log. A single boot can still fail before Gate 1 (B2, §2.6: 13 of 20 text boots of `main` 8fa4c24's kernel were CLEAN, and the other 7 died at a PC-zero or other H1 report), but the self-test lines of the ipc-timeout thread printed in 20 of 20 of those boots, about 6 s in, before the bench. So per-step boot checks grep only self-test lines, with the bench exception below. A boot that dies or wedges before them is re-run and the failure is noted. A boot that logs `slot moved` is also re-run for its step's acceptance, and noted. The bench exception: steps 13 and 14 also check that `[bench] IPC round-trip` reports 10000 iterations in a CLEAN boot (step 13's check comes from the ADR's step table; step 14's is this plan's own). A boot that prints the self-test lines and then dies or wedges before that bench line is re-run for the bench check only, and noted; the self-test, pinned-thread, order and tick-bound checks are judged on the first boot and are not re-judged on the re-run. Step 6's `[bench] Shared memory throughput` check applies only if that line prints, and never causes a re-run. A pinned-thread line (the ipc-timeout thread from step 4, the Dead-test helper from step 8, pid 14's thread from step 10 and the wake helper from step 11, all on CPU 2, which takes timer IRQs since step 200) that is missing, or that fails its order or tick-bound check, fails the step's check; it is not waived, and the boot is not re-run for a luckier result. The one exception is a halt of CPU 2 itself: if the log carries `EXCEPTION[CPU 2]` or a `[tripwire] … src=exc cpu=2` line, and the pinned thread's earlier lines come before that fault while the missing or failing line would have come after it (read with `aios soak --classify "$LOG"` and the log), the failure is CPU 2's pre-existing H1 halt, not the pinned thread's. That boot is re-run and noted as H1, as for a boot that dies before the self-test lines. B2 saw this in 2 of 20 text boots (runs 08 and 10: `src=exc cpu=2` at t = 232 and 409, about 0.35 s after the Kit-error line, after which CPU 2's tick froze while the boot carried on), inside the window where the waits that steps 5 and 9–14 add print their lines. The gpu-mode checks of steps 7, 8, 12 and 13 (`display handoff complete`) depend on open question 6, because a single gpu boot of today's kernel rarely reaches that line (B2: 2 of 10). Gate 1 is covered by the soak pair.
- Patterns that use `+` or alternation are run with `grep -E`.
- **Boot logs.** Each step saves its acceptance boot log as `target/cap-lifetime/step-N.log` (`target/` is gitignored); gpu-mode logs as `step-N-gpu.log`. The commands below use `LOG=target/cap-lifetime/step-N.log`. A boot's class can be read with `aios soak --classify "$LOG"` (step 1a's classifier).
- **No new kwarn.** Each step's normalised warning set must be a subset of the previous step's set plus an allowlist: `denied ChannelCreate` (printed in every text boot since step 200, B2 20 of 20, but in no gpu boot), `slot moved`, and any line the step's acceptance names as new. Lines the acceptance names as removed must be gone. The baseline is a boot of the PR's base commit, f410589, re-taken from a boot of the new base after any later update from `main` (first bullet). In B2's 20 text boots of `main` 8fa4c24's kernel (§2.6) the per-boot set is `denied ChannelAccess(N)` (11 per boot), `denied SharedMemoryAccess(N)` (2), `denied SharedMemoryCreate`, `denied ChannelCreate`, `shm_create: W^X violation (pid=N)`, `shm_map: flags not subset of max_flags (pid=N, region=N)`, `shm_unmap: not mapped (pid=N, region=N)`, `Timeout test: unexpected result -N`, `Destroy test: unexpected result Err(-N)` and `No DTB — using QEMU virt defaults`; three echo-client warnings appeared once each in 20 boots (`ipc_call failed with -N`, `error -N after service death (expected EPIPE)`, `channel endpoint still Active after service death`). The baseline boot decides the set.

```bash
grep -a ' WARN ' "$LOG" | sed -E 's/^\[[ 0-9.]+\] \[[0-9]\] //; s/[0-9]+/N/g' | sort -u
```

- **Timeout-last check.** From step 4, which moves the Timeout test last, the Timeout line must come after every other ipc-timeout test line. Before step 4 it prints first in the thread (§5.2). The log carries a CPU tag but no thread tag, so line order is the only check available. `Timeout-arg test:` (the PI pair's thread on CPU 3) is not an ipc-timeout line and matches neither pattern. Each step that adds a line adds its name to the pattern. The full pattern after step 14:

```bash
awk '/Timeout test:/ {t = NR} /(Destroy|Bad-id|Bad-pid|Select-cap|Syscall-arg|Kit-error|Stale-id|Stale-shm|Shm-cascade|Create-ABI|Share|Dead|Wake-token|Notify-loop|Select-loop|Sleep-loop|Recv-loop|Call-loop) test:|Lifecycle:/ {o = NR} END {exit !(t > o)}' "$LOG"
```

- **DAIF count.** `rg -c 'msr DAIFClr' kernel/src/sched/scheduler.rs kernel/src/ipc/direct.rs`, read per file, because rg does not print files in argument order: `scheduler.rs:7` and `direct.rs:8` at f410589 (unchanged since b640789), and at every step, because the four masked helpers of steps 8, 10 and 11 use `daif::with_irqs_masked` (`arch/aarch64/daif.rs:16`) and add no inline site (Decisions Made, 2026-10-11).
- **Re-run after an update from `main`.** Updates are merges (first bullet), so only the updated tip can be booted. The re-run at the tip is: (1) the latest done step's own checks; (2) every self-test line and count that any done step's check names, with the text or count in force at the latest done step, taken from §5.2's After and Step columns and the later steps' "except" clauses (for example, at a step-7 tip `denied ChannelAccess` is 8, the Timeout line is `ETIMEDOUT as expected` and last, and `shm_cascade: pid=1 destroyed 1` is 5); (3) the DAIF count (above), and from step 4 the Timeout-last pattern as extended up to that step. Steps 12–14's checks carry no "step-N lines unchanged" clause, so (2) is what carries the earlier lines at those tips. For no-new-kwarn, the tip's normalised warning set must be a subset of the base set re-taken from a boot of the new merge base, plus the lines the done steps' checks name as new, plus the allowlist ("No new kwarn"); every line those checks name as removed must be absent. Step 8 rewrites the comment at `scheduler.rs:211-218` ("Origin::Yield never gets here (thread_yield stores Running)"): a Dead thread that yields reaches that branch with `Origin::Yield`, and `n1` still counts only `Origin::Irq`.

A victim already Runnable at B is picked and set Running (`:276`). Since crash-fix step 200 (8fa4c24) every CPU takes timer IRQs: every tick sets `NEED_RESCHED` (`timer.rs:232`), and the IRQ path's `check_preemption` (`gic.rs:495`) calls `schedule(Origin::Irq)` (`scheduler.rs:508`), which does not re-queue a current thread that is not Running (`:210-223`). So a victim running on any CPU at B is lost if a tick's `schedule()` takes it off its CPU, and stays off every queue unless a stray `unblock` later revives it (`:449-460`), which the early return (step 8) removes; it is revived if a yield, a block or a direct switch takes it off first (`:365`, `:394`; `direct.rs:146`). Both direct switches already refuse a target that is not `BlockedIpc` (`direct.rs:87-99`, `:260-272`), so a Dead target takes the slow path. `TICK_COUNT` still advances only on CPU 0 (`timer.rs:200-201`).

The `unblock` early return and the pick filter also make a lost lock permanent (ADR §7). Until crash-fix step 8's preempt count, a tick can switch a victim away inside a `spin::Mutex` critical section (crash-fix H3), before or after B, on any CPU. Once it is Dead it never runs again, its lock is never released, and the next taker spins forever, for example C's `CHANNEL_TABLE` lock. A victim already Runnable at B is revived today by the pick's Running write (`scheduler.rs:276`); the pick filter drops it instead, so for that case this PR creates the lost lock. A victim running at B is lost this way today on every CPU, because a tick's `schedule()` does not re-queue it; only a stray `unblock` could revive it, and the early return removes that. A victim preempted inside owed work loses its wake or leaks the same way (ADR §7). Crash-fix step 8's preempt count removes both lost-lock cases; until then the interim exit rule (§6.3, Step 8) keeps such exits out, except the echo client's exit of pid 7 (§3 step 8), whose lost-lock signature §5.3 pre-registers for the soak pair.

`process_exit` has three runtime callers: SVC 24 (`syscall/mod.rs:716`), the echo client's exit of pid 7 (`service/mod.rs:455`, the one known exception) and, since #219, the echo client's exit-walk probe, which exits `EXIT_PROBE_PID = ProcessId(6)` (`service/mod.rs:344`, `:372`) from the pid-7 client before that client's own exit (`:451`, `:455`). Pid 6 has no `PROCESS_TABLE` slot and no thread, so B marks nothing Dead, no exit code is recorded and no waiter is woken (`process.rs:138-144`, `:213`); the interim rule allows that exit, but it makes the echo client a non-member caller (ADR §11's 2026-10-09 note, ADR line 282), which step 8's caller analysis and step 10 must count (open question 3).

**Today's B also marks the caller Dead** (`process.rs:146-154`) when it belongs to the exiting pid, as the echo client does at `service/mod.rs:455`. Since step 200 the client's CPU takes ticks, so a tick-driven `schedule(Origin::Irq)` anywhere between B and its next yield switches it off for good, including inside `process_exit`'s later `CHANNEL_TABLE` walk (`process.rs:166`), `channel_endpoint_states` (`service/mod.rs:331`) or `ipc_call` (`channel.rs:106`), which loses `CHANNEL_TABLE`. #219's comment at `service/mod.rs:346-349` states the same hazard. It predates this PR and was not hit in B2's 20 text boots (a window of about 0.3 ms per boot); step 8's `kill_process_threads` caller exclusion removes it.

(3) The thread's own swaps race safely with wakers: they are read-modify-writes on the same location as the waker's CAS, in one modification order. A future lock-free waker would need Release on the arm and Acquire on the lookup.

| Dead | any | `Dead` | Return: no token, no enqueue |
| Running or Runnable | Armed | `LeaveToken` | CAS to Woken; no state change, no enqueue |
| Running or Runnable | Woken | `TokenPending` | Nothing |
| Running or Runnable | Idle | `Skip` | Nothing; the wake is stale |

### Steps 11–14: shared loop contract and helpers

Introduced in step 11 and used by steps 12–14.

- **Own tid:** the site reads `me` once per wait through `sched::current_tid()`, added in step 11: `CURRENT_THREAD[core_id()]` read inside `daif::with_irqs_masked`. It replaces the site's `current_thread_id()` call, whose two reads with IRQs on can name another CPU's thread (crash-fix N4); `prepare_block` on that tid would arm the wrong word. It is not 1b's instrumentation-only `tripwire::current_tid(cpu)` (§2.5). A missing current thread returns EPERM.
- **Pass 1:** arm inside, or before, the critical section that publishes the first waker record, then publish the timeout entry or deadline after the arm, then block. There is no check between the publish and the block, so a normal wake is a `LeaveToken`, an `Enqueue` or a direct switch, never a `Skip`.
- **Pass ≥ 2:** first `prepare_block(me)`, after any fast path below. A condition that a waker writes under lock L may be checked in the same L critical section as the arm. Then evaluate the exits in the site's order, republish any record a waker removed, re-insert the timeout entry if it is missing, and block.
- **Fast path:** a check with no arm that publishes no waker record may come before pass 1. It may consume the condition under its own lock, as `notification_wait`'s (`notify.rs:189-207`) and `ipc_select`'s fast scans do. In `ipc_call`, a pre-arm read of `done` may also start a later pass after a switch (step 14); it publishes nothing, which ADR §8 rule 3 allows.
- **Every pass ends in `block_current` or `cancel_block`.** A pass that armed and then finds its deadline passed, a condition met or a failure calls `cancel_block(me)` before the next pass or the exit, so the next `prepare_block` finds Idle (its assertion is live in `just run` and the soak, which build the dev profile).
- **Exit:** remove own records and entries; in `ipc_call`, `ipc_recv` and `ipc_select`, the waits a non-zero `WAKEUP_ERRORS` code is aimed at, take it once and discard it; then `cancel_block(me)` if this pass armed. Every exit of these three waits takes it once, including an exit after the arm that returns without blocking, such as a pass-1 EAGAIN or Expired (owner, 2026-09-28); a return before any arm or publish (a fast path, `ipc_recv`'s pass-1 checks (1)–(3), `ipc_call`'s pass-1 failures) takes nothing (§3 steps 11, 13 and 14). `sleep_ticks`, whose own entry `check_timeouts` wakes with code 0 (`timeout.rs:123`, `:223`), and `notification_wait` do not take it. A stale code, a late non-zero one reaching a sleep included (`check_timeouts` wakes after dropping `TIMEOUT_QUEUE`, `:119-124`, so a late ETIMEDOUT from an earlier `ipc_call` can land during a sleep), decides nothing: the next `wake_with_error` to that thread overwrites it (`timeout.rs:154`), as a sleep's own timeout wake does with 0, or else the next `ipc_call`, `ipc_recv` or `ipc_select` exit discards it (ADR §9).
- **Result:** derived from object state and the wait's own deadline, never from which wake arrived.
- **1b's N2 phases.** Each converted pass keeps 1b's N2 phase instruments: `wait_published` in the publishing hold after the arm, `wait_armed` in `arm_timeout`, and `wait_ended` at the exit; the waker-side `mark_wake_pending` and `note_*` calls stay at each waker (§2.4). Both arms of the soak pair then classify N2 the same way.
- **Helpers.** Deadlines come from `shared::deadline_after` (#217, `shared/src/ipc.rs:39-47`), where `None` means no deadline. `timeout::arm_timeout(me, deadline, code) -> Armed | Expired` extends today's private `channel.rs::arm_timeout` (`:40-53`): it moves into `timeout.rs`, keeps `wait_armed` inside the `TIMEOUT_QUEUE` hold, reads `TICK_COUNT` inside that hold (`now >= deadline` gives Expired; otherwise it inserts the entry when the slot is `None`; a `None` deadline inserts nothing), and returns `Armed | Expired`, rather than a second helper beside it. Reading inside the hold orders it after any `check_timeouts` that removed the entry, so it never re-inserts an entry that already fired. `timeout::clear_own_timeout(me)` is `clear_timeout_blocking(me)` (step 10) and replaces `channel.rs:233-236` and `:352-355`. `notify::arm_deadline(me, deadline) -> Armed | Expired` and `notify::clear_deadline(me)` (sets `u64::MAX`).
- **Wake helper thread.** A new pid-1 thread, created at init and pinned to CPU 2. It polls an `AtomicU32` mailbox with `thread_yield` and runs one command at a given tick, then sets a done flag: `Stale { target, clear_timeout: bool }` (optionally `clear_timeout_blocking(target)`, recording whether it removed an entry, then `unblock(target)` under the `self_test` source); `Signal { n, bits }`; `Send { ch }`; `RecvBlock { ch, t }`. A test that asks for `clear_timeout: true` logs `stale clear missed` as a failure if no entry was removed, because it would then not exercise the re-insert.
- **Backstop.** Steps 12–14's tests arm `notify::arm_deadline(me, now + 200)` as a backstop, which relies on step 11's unconditional `check_notification_timeouts` (today `check_timeouts` reaches it at `timeout.rs:127` only after its own `TIMEOUT_QUEUE.try_lock` succeeded, `:97`). The backstop is cleared afterwards; if it already fired, its late `unblock` is one more stale wake, which the next test tolerates.

## 4. Why the order

- Steps 1–2 come before step 5. Landing #163 on bare ids would let pid 1's surviving `ChannelAccess(ch2)` from the Destroy test authorise whatever channel lands in ch2's slot next.
- Step 3 comes before step 5, which needs `mint_child` and `free_slots`.
- Step 4 comes before step 5, so the scheduling change lands and boots alone; if step 5's boot regresses, the capability change is the only new variable. Every CPU takes timer IRQs in the base (f410589), so the step-4 boot runs the pinned thread under the same scheduling as step 5's.
- Step 6 comes after step 5 (it needs `creation_cap` from minting, `is_revoked` from step 3 and `RegionSlot` from step 2) and before step 7, so the `bad_pid.rs`, `kit_errors.rs` and `syscall_args.rs` reorder and the stale-shm expectations are written once, against the cascade.
- Step 7 comes after steps 5 and 6: share-as-delegation needs the minted token, and the Kit destroy uses `region_detach`.
- Step 8 comes before step 9 (the token's Dead rows rely on its guards) and before step 10 (revoking pid 7's table without the guards leaves a killed thread able to be picked and to spin on EPERM). Step 9 comes before step 10, because `process_wait` arms.
- Steps 11–14 come after step 10, from least to most used: 11 serves boot self-tests only (the select_cap test's six `ipc_select` calls return before the arm), 12 serves gpu input, 13 the services and the bench server, 14 the bench client. - **Step 8.**
  - **The exit safe point** (second-set answer 3; §6.4's amendment; ADR §7). The owner's definition: an exit-pending flag checked at IRQ exit, syscall return and before blocking. The flag is set where B marks the thread Dead, and "before blocking" means on entry to `prepare_block` and `block_current` (ADR choice). A flagged thread leaves the CPU as Dead, with its wait word reset, only where it holds no lock: at `irq_exit` where preemptible, at syscall return, or at `block_current` entry. Holding no lock is not enough: if one of these lands inside owed work, the owed-work requirement (next item) applies, and the thread finishes that work, or has it finished for it, before it is dropped. `prepare_block` may be called inside the publishing critical section (rule 1, ADR §8, allows inside or before it), so on entry to `prepare_block` the check does not arm and never leaves the CPU; the thread leaves at its next `block_current` or syscall return (ADR choice). Once the safe point exists, `bw` counts Dead threads and reads 0.
  - **Owed work, a requirement on step 8** (owner, 2026-09-28; #185 comment 5860818900; ADR "Decisions" and §7). Step 8 must make sure that a thread B marks Dead is never left for good inside owed work, "a wake, frame free or publish it still owes another thread after releasing a lock" (#185): it finishes the work, or has it finished for it, before it is dropped, whatever took it off its CPU (an exit-flag check, a slice-expiry preemption or a tick before B). Counting frame frees and publishes that no other thread is owed (the leak cases) is the ADR's reading, not the owner's words. ADR §7's examples: `channel_destroy_unchecked` between its `drop(table)` and its two `wake_with_error` calls (`ipc/mod.rs:257-262`), which leaves a peer in a no-timeout `ipc_call` (`channel.rs:129-133`) Blocked with no waker, and C cannot help, because the victim has already taken the channel out of the table (a peer with a deadline is woken only at its deadline and gets a late EPIPE, by ADR §9's exit order, §3 step 14); a frame free after a detach; a publish after an allocation. It includes work whose wake is itself a direct switch, such as `ipc_call`'s `try_direct_switch` (`channel.rs:183`) and `ipc_reply`'s `try_reply_switch` (`:459`). Step 8's caller analysis counts the probe.
  - **Off-CPU wait between B and C** (ADR §7, ADR choice). Step 8 defers exit step C until every victim other than the caller is off CPU, so C also removes anything a victim published before it left. After B, with no lock held and IRQs as at entry (unmasked for EL1 callers, masked on the SVC 24 path; the Step 2 item above), `process_exit` waits on each such victim's `on_cpu` (6a's per-thread flag); no per-process count is needed. A Blocked or Runnable victim is already off CPU, or is once its last switch completes. A running victim's `on_cpu` clears at whichever switch takes it off: a safe point, `try_reply_switch` or `thread_yield`. After that it never runs again, because `schedule()` does not re-queue a Dead thread and the pick drops one. So the wait lasts about one tick plus the longest lock hold or owed-work span, and the owed-work term depends on step 8's mechanism. `process_exit` then runs C, D and E in order, so E still publishes the exit code last.
  - **The exit wait's own bound** (ADR choice). The wait does not use 6a's iteration count (crash-fix `:171`), which is sized for switch tails and would turn a healthy exit into a false PANIC. It reads `CNTPCT_EL0` when it starts and panics with the victim's tid once 100 ms of counter time has passed (`CNTFRQ_EL0` / 10 increments, 6,250,000 at QEMU's 62.5 MHz). That covers one tick, the longest lock hold or owed-work span, and a margin for a vCPU descheduled under TCG at the soak's load rule, and stays well below the soak harness's 15 s default stall window (`--stall-secs`). The counter advances with IRQs masked and on every CPU, whereas `TICK_COUNT` advances only on CPU 0 (`timer.rs:200-201`), so a tick bound would never expire for a masked caller on CPU 0. The one-tick term assumes that every CPU takes timer IRQs, which holds since step 200. On the SVC 24 path the caller's CPU spins with IRQs masked for up to about one tick plus the longest lock hold or owed-work span (ADR choice). That is safe: each victim's safe points run on its own CPU, the caller holds no lock, and the wait is bounded in counter time. Not chosen (ADR Review notes, third audit rounds 2–4): a per-process pending-victim count, unmasking in `sys_process_exit` before the wait, and reusing 6a's constant.
  - **Added acceptance** (ADR §7 and its step-8 constraint; the amendment's "Added acceptance"). A boot self-test exits a process whose thread is running on another CPU; that thread reaches a safe point, and afterwards no waiter record of it remains (ADR choice). An exit that lands while a victim is in `channel_destroy`, with another process's thread in a no-timeout `ipc_call` on that channel, still delivers EPIPE to that caller (owner, 2026-09-28); it checks one instance of the owed-work requirement, `channel_destroy`'s EPIPE wakes, and relies on `ipc_call` with `timeout_ticks == 0` staying unbounded, which ADR §9 keeps as a recorded deviation from `docs/kernel/deadlock-prevention.md` §4.2 (§3 step 14).   - **Interim rule until step 8 lands** (ADR §7; the amendment's step-8 bullet). `process_exit` is called only when no victim other than the caller can be Running or Runnable at B: none of another process's threads, and in a self-exit none of the caller's sibling threads. That holds when the process has no other threads, or when each of them is Blocked and nothing can wake it before B. One check that a victim is Blocked is not enough, because a woken victim can run and be preempted holding a lock, or inside owed work, before B. The reason is the lost lock (§2.3): until step 8's preempt count, a tick can switch a victim away inside a `spin::Mutex` critical section (crash-fix H3), and once it is Dead it never releases the lock, so the next taker, for example C's `CHANNEL_TABLE` lock, spins forever. A victim running at B, on any CPU since step 200, is lost this way already, because `schedule()` does not re-queue it; that loss predates this PR. A victim already Runnable at B is revived by today's pick, and this PR's pick-drop creates its loss. The rule keeps the lost wake out too: until step 8 meets the owed-work requirement, a victim that a tick takes off its CPU inside owed work, before or after B, never finishes that work. A Blocked victim is taken to hold no lock and owe no work, on the assumption that nothing blocks while holding a spin lock or owing work; step 8's sleeping-while-atomic panic enforces the first (crash-fix `:535`), and its owed-work mechanism must keep the second. This PR's lifecycle self-tests meet the rule (§3 step 10), and the probe's exit of thread-less pid 6 meets it too. The echo client's exit of pid 7 predates this PR, is exposed at every text boot since step 200, and is the one known exception (§3 step 8; §5.3 pre-registers its lost-lock signature). No new caller of that kind is added. Step 8 lifts the rule: its preempt count keeps a victim from being switched off inside a `spin::Mutex` critical section, and its owed-work mechanism makes sure a victim is never left for good inside owed work.

## Open questions (2026-10-11 reconcile)

- **Question 2: 1b's Dead outcomes after step 8.** Step 8 must take Dead out of `UnblockKind::Revived` (`ubdead`, which counts "made Runnable"), and decide whether a Dead thread still queued while it waits for the pick filter counts as `qbad`. Nothing in `kernel/` writes `Suspended`, `BlockedTimer` or `BlockedIo` today, so in practice `ubdead` counts only Dead targets in both arms. Options: (A) keep the key `ubdead`, redefined as "`unblock` reached a Dead target" (skipped from step 8, `made_runnable()` false), fold the unused `Suspended`/`BlockedIo` into `Woke` and move `BlockedTimer` to `Woke` in step 12, and treat a queued Dead thread as clear, not `qbad`; (B) add a new key for the Dead skip and keep `ubdead` for revivals of the other states; (C) rename `ubdead` (for example `ubrev`) and add a Dead-skip key. **Recommendation: A.** The key list and positions stay the same in both arms, the key's name matches what it then counts, and a lazily dropped Dead thread is by design, not a bad queue entry; B and C change the catalogue the soak parser and its goldens read, and the arms then differ.
- **Question 3: The exit-walk probe's exit of pid 6.** From step 10, step A returns EPERM for an Empty slot, so #219's probe (`service/mod.rs:372`) breaks, and the ADR's 2026-10-09 note leaves the fix open. Options: (A) install pid 6 (no parent, no threads) before that exit, which keeps the probe in the echo client, uses pid 6's slot for good (slots are never reused), and keeps the echo client a non-member caller of `process_exit`; (B) move the probe into `ipc/tests/lifecycle.rs`, run from pid 1 on a lifecycle pid, keeping its expected line. **Recommendation: B.** Pid 1 is already the caller every interim-rule argument relies on, the echo client becomes a pure self-exit again (one fewer case for step 8's caller analysis), and the probe sits with the other exit tests.
- **Question 4: Tripwire index sets across the soak pair's arms.** 1b's per-source and per-lock keys are positional (`WakeSource::ALL`, 15 wide; `LockClass::ALL`, 9 wide). Step 11 deletes `SelCall`, `SelSend`, `SelSig`, `Nsto` and `SELECT_WAITERS`, step 8 adds a `self_test` source, and the pair is read by one harness binary, so one arm's columns would be labelled by the other arm's sets. Options: (A) keep both sets at their current width and order in this PR (deleted entries print 0 in the branch arm, `self_test` appended at the end) and drop the dead entries in a follow-up PR after the soak, which conflicts with your no-legacy rule; (B) change the sets in this PR, bump `SCHEMA_VERSION` to 2, and teach the soak parser to decode `v=1` lines with the v1 sets and `v=2` lines with the new ones, then run the pair from the branch tip's harness; (C) change the sets freely and compare only the non-positional keys across arms, giving up the per-source `Skip` comparison §5.3 relies on. **Recommendation: B.** It keeps the kernel free of dead entries, both arms stay decodable, and the v1 table stays in use for every existing soak log (B1, B2 and the `main` arm).
- **Question 5: `NOTIFICATION_TABLE`'s lock class after step 11.** The ADR's step-2 inventory change takes `NOTIFICATION_TABLE` out of the IRQ path, but 1b's heartbeat scan still reads it from IRQ context (`ipc/scan.rs:101-115`).
