- **Boot checks** run as one of those verifier boots and grep its UART log `$LOG`. A single boot can still fail before Gate 1 (B2, §2.6: 13 of 20 text boots of `main` 8fa4c24's kernel were CLEAN, and the other 7 died at a PC-zero or other H1 report), but the self-test lines of the ipc-timeout thread printed in 20 of 20 of those boots, about 6 s in, before the bench. So per-step boot checks grep only self-test lines, with the bench exception below. From step 11 the loop tests' timed-out waits keep the ipc-timeout thread busy for about 10 s more (§3 "Scheduling on CPU 2"), so its later lines (the loop tests, then the Timeout test) print after the bench, and a boot that dies after Gate 1 can lose them. A boot that dies or wedges before a checked line prints is re-run for the checks it missed, and the failure is noted. A boot that logs `slot moved` is also re-run for its step's acceptance, and noted. UART output from several CPUs is unlocked, so a line can be torn by another CPU's output (B2 run-10: `process_exit: 000000pid=7`, §2.6). A line that a strict grep does not find, or a `grep -c` count that comes out short, is read by hand in the log for a torn copy before the line counts as missing. A torn copy is the line's characters in order with another CPU's output inserted between them, which can be heavy (B2 run-08's `EPIPE after service death (expected)` is spread through a tripwire dump, `run-08.log:255`); it counts as printed, and the step's report notes it. The bench exception: steps 13 and 14 also check that `[bench] IPC round-trip` reports 10000 iterations in a CLEAN boot (step 13's check comes from the ADR's step table; step 14's is this plan's own). The self-test checks and the bench check are judged independently: a boot that lacks the lines of one of them because it died or wedged first is re-run for that check only, and noted, and a check already judged on an earlier boot is not re-judged on the re-run. Step 6's `[bench] Shared memory throughput` check applies only if that line prints, and never causes a re-run. A pinned-thread line (the ipc-timeout thread from step 4, the Dead-test helper from step 8, pid 14's thread from step 10 and the wake helper from step 11, all on CPU 2, which takes timer IRQs since step 200) that is missing, or that fails its outcome or order check, fails the step's check; it is not waived, and the boot is not re-run for a luckier result. **Outcome-only** (owner, 2026-10-11, Q8): no check reads elapsed ticks as a pass band. A pinned-thread check judges which wake source fired, the order of events and the waiter and deadline state left behind, and every deadline or safety entry it relies on is long enough (on the order of 2000 ticks) that crowding on CPU 2 by boot test threads A–D or by any Interactive thread cannot flip the outcome; how fast the waits return is left to the soak pair (§3 "Scheduling on CPU 2"). A pinned-thread poll is bounded in yields, not ticks: the Normal queue is FIFO (`sched/mod.rs:60-84`), so after a yield every Normal thread queued ahead on CPU 2 runs once before the yielder runs again, however long each runs (steps 8, 10 and 11). A thread that never blocks again would starve CPU 2's Normal threads outright rather than crowd them: the bench server and bench main are Interactive with `CpuSet::all()` and end in `wfe` loops after Gate 1 (`bench.rs:205-207`, `:463-465`), and `unblock` queues a woken thread on the waking CPU (`scheduler.rs:473-479`), so a final timeout wake from CPU 2 would park one there for good. Step 4 pins both to CPU 0 (§3 step 4). The one remaining exception is a halt of CPU 2 itself: if the log carries `EXCEPTION[CPU 2]` or a `[tripwire] … src=exc cpu=2` line, and the pinned thread's earlier lines come before that fault while the missing or failing line would have come after it (read with `aios soak --classify "$LOG"` and the log), the failure is CPU 2's pre-existing H1 halt, not the pinned thread's. That boot is re-run and noted as H1, as for a boot that dies before the self-test lines. B2 saw this in 2 of 20 text boots (runs 08 and 10: `src=exc cpu=2` at t = 232 and 409, about 0.35 s after the Kit-error line, after which CPU 2's tick froze while the boot carried on), inside the window where the waits that steps 5 and 9–14 add print their lines. - **Reading boot logs.** These apply to every check that reads a verifier run log:
  - A soak `run-NN.log` is binary-detected (firmware escape bytes) and sits under gitignored `target/`, so a recursive Grep or Bash-tool `grep` over the run directory skips it and a zero count there means nothing (rule 10, "Search Commands"). ### Step 4: pin the ipc-timeout thread

- The ipc-timeout thread (`ipc/tests/mod.rs:198-214`) is pinned to CPU 2 (`CpuSet::single(2)` in place of `CpuSet::all()` at `:209`; it is already queued on CPU 2 at `:214`) from creation, and the Timeout test moves to the end of `ipc_timeout_entry`, after the Kit-error test. - **Why.** From step 5 the Timeout test really blocks for 100 ticks, and its wake comes from `check_timeouts` in timer-IRQ context. Pinned, `unblock` queues it on CPU 2 whichever CPU wakes it, through its "first allowed CPU" branch when the waker is another CPU, and CPU 2's own tick then preempts whatever runs there (`test-C` included) at slice expiry (`scheduler.rs:198-205`). The result is one IRQ-context wake per boot on the crash-fix H3 lock path, from whichever CPU sees the expiry first. It is not in N7's class: the thread cannot migrate, and CPU 2 is its last CPU, so 1b's `ubmove` should not count it (§6.2). Moving the test last means a late wake can hide only its own line.

### Steps 11–14: shared loop contract and helpers

Introduced in step 11 and used by steps 12–14.

- **Own tid:** the site reads `me` once per wait through `sched::current_tid()`, added in step 11: `CURRENT_THREAD[core_id()]` read inside `daif::with_irqs_masked`. It replaces the site's `current_thread_id()` call, whose two reads with IRQs on can name another CPU's thread (crash-fix N4); `prepare_block` on that tid would arm the wrong word. It is not 1b's instrumentation-only `tripwire::current_tid(cpu)` (§2.5). A missing current thread returns EPERM.
- **Pass 1:** arm inside, or before, the critical section that publishes the first waker record, then publish the timeout entry or deadline after the arm, then block. There is no check between the publish and the block, so a normal wake is a `LeaveToken`, an `Enqueue` or a direct switch, never a `Skip`.
- **Pass ≥ 2:** first `prepare_block(me)`, after any fast path below. A condition that a waker writes under lock L may be checked in the same L critical section as the arm. Then evaluate the exits in the site's order, republish any record a waker removed, re-insert the timeout entry if it is missing, and block.
- **Fast path:** a check with no arm that publishes no waker record may come before pass 1. It may consume the condition under its own lock, as `notification_wait`'s (`notify.rs:189-207`) and `ipc_select`'s fast scans do. In `ipc_call`, a pre-arm read of `done` may also start a later pass after a switch (step 14); it publishes nothing, which ADR §8 rule 3 allows.
- **Every pass ends in `block_current` or `cancel_block`.** A pass that armed and then finds its deadline passed, a condition met or a failure calls `cancel_block(me)` before the next pass or the exit, so the next `prepare_block` finds Idle (its assertion is live in the verifier's boots and the soak, which build the dev profile).
- **Exit:** remove own records and entries; in `ipc_call`, `ipc_recv` and `ipc_select`, the waits a non-zero `WAKEUP_ERRORS` code is aimed at, take it once and discard it; then `cancel_block(me)` if this pass armed. Every exit of these three waits takes it once, including an exit after the arm that returns without blocking, such as a pass-1 EAGAIN or Expired (owner, 2026-09-28); a return before any arm or publish (a fast path, `ipc_recv`'s pass-1 checks (1)–(3), `ipc_call`'s pass-1 failures) takes nothing (§3 steps 11, 13 and 14). `sleep_ticks`, whose own entry `check_timeouts` wakes with code 0 (`timeout.rs:123`, `:223`), and `notification_wait` do not take it. A stale code, a late non-zero one reaching a sleep included (`check_timeouts` wakes after dropping `TIMEOUT_QUEUE`, `:119-124`, so a late ETIMEDOUT from an earlier `ipc_call` can land during a sleep), decides nothing: the next `wake_with_error` to that thread overwrites it (`timeout.rs:154`), as a sleep's own timeout wake does with 0, or else the next `ipc_call`, `ipc_recv` or `ipc_select` exit discards it (ADR §9).
- **Result:** derived from object state and the wait's own deadline, never from which wake arrived.
- **1b's N2 phases.** Each converted pass keeps 1b's N2 phase instruments: `wait_published` in the publishing hold after the arm, `wait_armed` in `arm_timeout`, and `wait_ended` at the exit; the waker-side `mark_wake_pending` and `note_*` calls stay at each waker (§2.4). Both arms of the soak pair then classify N2 the same way.
- **Helpers.** Deadlines come from `shared::deadline_after` (#217, `shared/src/ipc.rs:39-47`), where `None` means no deadline. `timeout::arm_timeout(me, deadline, code) -> Armed | Expired` extends today's private `channel.rs::arm_timeout` (`:40-53`): it moves into `timeout.rs`, keeps `wait_armed` inside the `TIMEOUT_QUEUE` hold, reads `TICK_COUNT` inside that hold (`now >= deadline` gives Expired; otherwise it inserts the entry when the slot is `None`; a `None` deadline inserts nothing), and returns `Armed | Expired`, rather than a second helper beside it. Reading inside the hold orders it after any `check_timeouts` that removed the entry, so it never re-inserts an entry that already fired. `timeout::clear_own_timeout(me)` is `clear_timeout_blocking(me)` (step 10) and replaces `channel.rs:233-236` and `:352-355`. `notify::arm_deadline(me, deadline) -> Armed | Expired` and `notify::clear_deadline(me)` (sets `u64::MAX`).
- **Wake helper thread.** A new pid-1 thread, created at init and pinned to CPU 2. It polls an `AtomicU32` mailbox with `thread_yield`, takes one command at a time, records the tick it acted at, and sets a done flag. Commands: `Stale { target, clear_timeout: bool }`: keep polling until the command's due tick has passed and the target's wait has published the record the command acts on, its `TIMEOUT_QUEUE` entry for `clear_timeout: true` and otherwise its notification deadline (`NOTIFY_DEADLINES[target] != u64::MAX`); then optionally `clear_timeout_blocking(target)`, recording whether it removed an entry, then `unblock(target, WakeSource::SelfTest)`. `Signal { n, bits }`; `Send { ch }`; `RecvBlock { ch, t }` (`ipc_recv(ch, …, t)`, recording its result). Waiting for the target's record puts the stale wake inside the wait however the two threads are scheduled, so a `clear_timeout: true` command finds the entry on a correct kernel, and a test that asks for it logs `stale clear missed` as a failure if no entry was removed (it would then not exercise the re-insert). After its wait returns, the driver sets a case-over flag; a `Stale` command still waiting for its record when that flag is set is abandoned and recorded as such. The driver then yields until the done flag is set (at most 32 yields, §1) and logs its case's failure line, naming the helper, if the command was abandoned or the flag is still clear, so a late command never lands in the next case.
- **Scheduling on CPU 2** (owner, 2026-10-11, Q8: outcome-only; settled, and not reopened by reviews). The loop tests drop every elapsed-time pass band and the CPU-2 timing model of the earlier draft. CPU 2 is crowded at times: boot test thread C is Normal on CPU 2 and never yields after its iterations (`sched/init.rs:78-92`, `:183-187`), the load balancer can move A, B or D there (`sched/init.rs:236-268`), each of them runs a full 50-tick slice when picked (`scheduler.rs:198-209`), and any Interactive thread queued there runs before every Normal one (`sched/mod.rs:73-84`). Crowding only delays the pinned threads, and each test is built so that a delay cannot change its outcome:
  - **What a test checks.** Which wake source fired: the result the wait returned, and in steps 12–14 whether the backstop had fired (below). The order of events: the helper's stale wake landed inside the wait (guaranteed by the helper's wait for the target's record, and failed loudly if abandoned), and a wait that timed out did not return before its own deadline (`TICK_COUNT` ≥ the deadline when it returns, which a delay can only make truer). The state left behind: no waiter record or select registration, `waiting_receiver`, `pending_caller` and `REPLY_SLOTS[me]` `None`, no `TIMEOUT_QUEUE[me]` entry, and `NOTIFY_DEADLINES[me] == u64::MAX` once the wait's exit or the test's backstop clear has run.
  - **Deadlines.** Every loop-test wait uses a 2000-tick timeout or deadline; steps 12–14's backstop expires 2000 ticks after the wait's own deadline; helper commands are due at +5. A delivered early wake returns when the driver next runs, and a lost one only at the deadline, with a result (ETIMEDOUT, or a backstop wake) that names the loss. 2000 ticks is the owner's margin over crowding: B2 never put more than three never-yielding test threads on CPU 2 at once, a delay of a few 50-tick slices, so crowding cannot push a helper's act past a deadline, let a deadline expire before a delivered wake is seen, or let a backstop fire before a driver woken by its own deadline has run.
  - **Cost.** The five timed-out waits (`Notify-loop` (a), `Select-loop` (a), `Sleep-loop`, `Recv-loop` and `Call-loop`) take about 2 s each, so from step 11 the ipc-timeout thread runs about 10 s longer and prints its later lines after the bench (§1, "Boot checks"); a lost wake costs up to 2 s more. No check orders those lines against the bench, and step 4's pin of the bench server and bench main to CPU 0 keeps an Interactive `wfe` loop from starving CPU 2 in that time (§3 step 4). How fast the waits return is left to the soak pair.
- **Backstop.** Steps 12–14's tests arm `notify::arm_deadline(me, deadline + 2000)` before their wait, where `deadline` is the wait's own: an independent wake source, so a wait whose own timeout entry was lost returns and logs its failure line instead of hanging. It relies on step 11 running `check_notification_timeouts` on every tick (§3 step 11), not only after `check_timeouts`' own `TIMEOUT_QUEUE.try_lock` succeeds (today `timeout.rs:97-100` returns early and `:127` is skipped). When the wait returns, the test reads `NOTIFY_DEADLINES[me]`: still its backstop value means the wait's own wake source ended it; `u64::MAX` means the backstop fired first, which logs `entry lost`. The test then clears the backstop with `notify::clear_deadline(me)`; if the backstop fired, its `unblock` is one more stale wake, which the next test tolerates.
